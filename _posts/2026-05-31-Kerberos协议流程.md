# Kerberos 协议流程
## 对象
Client (用户/客户端)：想访问服务的你。

Server (目标服务)：你想访问的资源（如 SQL 数据库、文件共享）。

KDC (Key Distribution Center - 密钥分发中心)：域控上的核心服务。它又分为两个窗口：

+ AS (Authentication Service)：负责核实你的身份，发“入场券”。

+ TGS (Ticket Granting Service)：负责发“项目票”。
## 流程

为了安全，Kerberos 认证分为三个阶段，每个阶段都是一次“请求与响应”。

**第一阶段：AS请求**

你向AS证明你是谁。

1.请求：你发送你的用户名。为了证明是你本人，你会用你的密码哈希对当前时间戳进行加密。

2.响应：AS用它存储的你的密码hash解密，发现时间戳是对的，说明密码正确。他会给你一张TGT（Ticket Granting Ticket - 票据授权票），即“入场券”。

**第二阶段：TGS请求**

你用TGT请求TGS，请求访问某个服务。

1.请求：你发送TGT和你要访问的服务的名称给TGS。

2.响应：TGS确认 TGT 合法，给你一张 ST (Service Ticket)，即“服务票据”。

    补充：TGS怎么确认TGT合法？

    简单来说，TGS 确认 TGT 是否合法，靠的是“只有 KDC 才知道的秘密”以及“时序验证”。核心机制是双重解密与校验。

    当 TGS 收到你的请求（TGS-REQ）时，你发给它的是两样东西：
    
    TGT 票据：它是被加密的。

    Authenticator（身份验证器）：也是被加密的。

    第一步：解密TGT

    TGT是在AS阶段生成的，它使用域内的krbtgt的NTLM Hash进行加密。

    由于TGS和AS服务都在KDC内部，所以他们共享krbtgt的密钥。TGS接到请求后，会使用知道的krbtgt的Hash进行解密。如果解密失败，则证明这个TGT不是由合法的DC签发的，直接拒绝。

    第二步：提取Session Key

    解密TGT成功后，TGS会从TGT的密文中提取出一个关键信息：Login Session Key（登录会话密钥）

    这个Session Key是AS阶段随机生成的，只有KDC和客户端（你）知道。

    TGT就像一个信封，里面装着这个Key，只有持有krbtgt密钥的TGS才能看到这个Key。

    第三步：验证Authenticator（身份验证器）

    为了防止重放攻击（即攻击者拿到了你的TGT来冒充你），客户端在发送TGT的同时还会发一个Authenticator（通常包含你的用户名和当前时间戳）。

    这个Authenticator是用客户端提到的Login Session Key进行加密的。TGS拿到刚才提取出来的Key，就会尝试去解密Authenticator。如果能解开，就说明发送者确实拥有这个Session Key。证明了TGT是合法的。



**第三阶段：服务请求**

1.请求：你发送 ST 和请求给服务。

2.响应：服务用自己的密码哈希解密 ST ，如果解密成功，说明票据是域控发的，就允许访问。

## 为什么这个协议要设计得这么复杂？

+ 密码不传输：整个流程中都没有明文密码在网络上传输，传输的都是hash和加密后的票据。

+ 防止重放攻击：每个请求都带着时间戳，即使攻击者截获了票据，过了有效期（一般是五分钟）后就失效了。

+ 双向验证：不仅服务器要验证你，你也可以验证服务器，防止中间人伪造服务器。
